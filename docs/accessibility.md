# Accessibility of the documentation portal

The documentation portal is part of the product and must be usable by
everyone: WCAG 2.2 level AA (NFR-A11Y-001, NFR-A11Y-002, QAS-INT-02).
Automated checks run on every pull request; a person checks what tools
cannot, once per minor release.

## Automated, on every pull request

The `Documentation portal` CI job builds the portal and checks it.
`make docs` and `make docs-a11y` run the same checks locally.

| Check | Script | Fails on |
|---|---|---|
| Internal links | `scripts/docs-check.pl`, part of `scripts/docs-build.sh` | a link or image to a file the portal does not serve, a fragment that names no id of its page, a link out of the site |
| Duplicate ids | the same | an id used twice on one page |
| Diagrams | the same | a Mermaid diagram not followed by a paragraph starting `Text description:`; an image without alt text; an inline SVG without a `<title>` |
| No third party | the same | a page that loads a stylesheet, font, script, image, frame or media file from another host, in a tag or in CSS (`url()`, `@import`); a link to another site is not a request |
| No third party, at run time | `scripts/docs-offsite.sh` (headless Chrome, `scripts/a11y-tools/offsite.js`) | any request a page makes, its scripts' included, to a host other than the site itself; off-site requests are aborted, so the check contacts no host |
| WCAG 2.2 AA | `scripts/docs-a11y.sh` (pa11y-ci with axe, headless Chrome) | on the guide pages, every axe result: a violation of any impact, and a result axe could not decide by itself ("needs review"); on the API reference, a rule whose count of distinct failures rises above `scripts/docs-a11y-baseline.json` |

Each check prints the pages it read and fails closed: a site without pages,
a page the browser could not load, or a report it could not read is a
failure, never a pass. External links are not fetched. Self-tests prove each
check can fail: `scripts/docs-html.test.sh`, `scripts/docs-check.test.sh`,
`scripts/docs-a11y.test.sh`, `scripts/docs-a11y-guards.test.sh`, and
`scripts/docs-a11y-runner.test.sh`, the unit test of the axe runner held to
100 % coverage, and `scripts/docs-offsite.test.sh`, which plants a Google web
font, a font file, a script, an image and a stylesheet added at run time,
and holds `offsite.js` to 100 % coverage.

### No request to a third party

Opening a page of the portal contacts no host but the portal's own. A web
font, stylesheet or script from another host would hand that host the
visitor's address before any consent. So the pages use the system font
stack; the API reference is built with Redoc's Google fonts switched off and
the same font stack; Redoc's script is served from the portal itself (the
build fetches the version the Redocly CLI names from the npm registry and
refuses it unless its sha384 is the one the CLI wrote), with its MIT licence
beside it (`redoc.LICENSE.txt`). The one change to that script is that its
sidebar credit no longer loads Redocly's logo from Redocly's CDN; the
credit's text stays. The README's status badges are images from another host
and appear on GitHub only, not in the portal.

The API reference (`reference.html`) is generated by Redoc, which we do not
write. Its axe results are printed as notes and counted as **distinct
failures**, so that the example content Redoc renders (a longer example
response draws more highlighted strings) does not move the count:

- `color-contrast`: one failure per colour pair and where it came from. The
  runner `scripts/a11y-tools/axe-runner.js` reports it:
  - `axe`: the text and background colour axe compared;
  - `computed`: axe could not compare them (a "needs review" result, such as
    text in a scrolling code panel), so the element's computed text colour
    and the nearest background colour painted at or above it;
  - undetermined: no pair can be read off the styles (no element, a
    background image, an opacity below 1, or a partly transparent
    background). These are counted one failure per place, like other rules.
- any other rule: one failure per place, the axe selector with its
  `nth-child` and `nth-of-type` parts removed and every number replaced, so
  that the tenth row of a table is the same failure as the first.

The count of distinct failures per rule is held against the committed
baseline `scripts/docs-a11y-baseline.json`: a rule above its count, or a rule
not listed, fails. The baseline may only go down:
`scripts/docs-a11y-ratchet.sh` fails a pull request whose baseline raises a
count, or adds a page or rule, compared with its base. When a count falls
below the baseline, the check says so and the baseline is lowered in the same
pull request.

A raise that is deliberate (a Redoc upgrade that brings a new failure we
accept) is declared, with its reason, by a line in the message of a commit
of the pull request that changes the baseline file, naming the page, the
rule and the exact new count:

```text
A11y-Baseline-Raise: reference.html color-contrast 12 — Redoc 3 highlights enum values in a new colour
```

The line is read anywhere in the message, so it survives a squash merge,
where it lands in a middle paragraph. The ratchet accepts a raise only when
such a line matches it, prints each accepted raise with its reason, and
fails a raise with no line, a line for another count, or one with no
reason. A base that already has the check but no baseline file is refused
rather than treated as the first baseline.

The checker is pinned by `scripts/a11y-tools/package-lock.json` (pa11y-ci,
pa11y, axe-core) and installed there with `npm ci --ignore-scripts`, so no
install script runs and no browser is downloaded; the system's Chrome is
used (`CHROME_PATH` to choose one).
`scripts/docs-a11y-pins.sh` fails unless every copy of pa11y in the lock,
top-level or nested under another package, is 10.0.0 and every copy of
pa11y-ci is 5.0.0, the versions the dependency review's licence exception
(LGPL-3.0) was reviewed for.

Mermaid diagrams are shown as their source text, not drawn: the text
description after each one carries its meaning, and it is what the check
requires.

## Writing accessible pages

- **Every diagram has an equivalent text description.** Put a paragraph
  starting `Text description:` right after a Mermaid block, saying what the
  diagram says, not what it looks like. Give every image an alt text that
  carries its meaning.
- Use headings in order, without skipping a level.
- Link text says where the link goes; never "click here".
- Never carry meaning by colour alone.

## Manual pass, once per minor release

Done by a maintainer on the portal built from the release candidate
(`make docs`, then open `site/index.html`), in a current browser and one
screen reader (VoiceOver, NVDA or Orca). Record the result in section 6 of
the release's test completion report: date, tester, browser and screen
reader with versions, each item's result, and every finding with its issue.

**Keyboard only (no mouse)**

- [ ] Every page: `Tab` reaches "Skip to content" first, and it moves the
      focus to the main content.
- [ ] Every link, button and scrolling code block or table can be reached
      with `Tab`, in reading order, and the focus is always visible.
- [ ] Wide code blocks and tables scroll with the arrow keys once focused.
- [ ] The API reference: the operation list, each operation, the request and
      response samples and the "Copy" buttons work with the keyboard alone.
- [ ] Nothing traps the focus.

**Screen reader**

- [ ] Each page announces its title and its language (English).
- [ ] The heading list of each page reads as an outline of the page.
- [ ] The navigation is announced as "Documentation" navigation, and the
      current page as current.
- [ ] Tables are read with their header cells.
- [ ] Every diagram's text description is read, and says what the diagram
      says.
- [ ] The API reference: the operation and parameter names, the required
      markers and the response codes are read.

**Display**

- [ ] At 400 % zoom (320 CSS pixels wide) no page needs horizontal scrolling
      except inside code blocks and tables, and nothing is cut off.
- [ ] With text spacing increased (line height 1.5, letter spacing 0.12 em,
      word spacing 0.16 em) no text is cut off or overlaps.
- [ ] The portal's palette still has these contrast ratios (recompute them
      if the colours in `scripts/docs-build.sh` changed): text `#1a1a1a` on
      the page `#ffffff` 17.4:1 and on code `#f4f4f4` 15.8:1; links and the
      focus outline `#0b57d0` on `#ffffff` 6.4:1 and on `#f4f4f4` 5.8:1;
      table borders `#767676` on `#ffffff` 4.5:1. Text needs 4.5:1 (WCAG
      1.4.3), borders and the focus outline 3:1 (WCAG 1.4.11).
